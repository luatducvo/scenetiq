# Spatial Queries parsed into objects and Relations, solved on stored geometry

A Query such as "the chair near the window" was ranked as one text against every Instance, so the words about the window only blurred the ranking, and the centroids and bounding boxes every Reconstruction stores (in metres, up is −Y by ADR 0007) were never used.

Every Query now goes through a parser that returns a parsed Query: up to four objects, each a short English phrase; the object the user wants; up to four constraints, each a Relation from a closed set, a subject and its Anchors; and the parts of the Query the set cannot express. The parser will be a schema-forced generation on the resident vision-language model (ADR 0008); until it exists, the real backend reads every Query as one without a Relation, and the tests use a fake.

A Query without a constraint is answered exactly as before, with its original text. Otherwise each object's phrase is ranked with the plain Query ranking, and its first M Instances (5 by default) are shortlisted; the wanted object takes `query_top_k` when that is larger. A candidate margin then drops the shortlisted Instances that fit the phrase much worse than the best one. On each of two channels, the cosine of the best-matching Description and the image similarity, an Instance passes when its similarity is no more than that channel's margin below the highest on that channel among the object's shortlist (0.1 for the Caption channel and 0.05 for the image channel by default; one margin per channel, because the two similarities are on different scales). An Instance stays a candidate when it passes on either channel, so one without a Caption is judged on the image channel alone, and candidates keep their fused order. The margin is relative: the best of each channel always stays, every object keeps at least one candidate, and a spatial Query returns between one and `query_top_k` Matches. A deterministic solver scores every assignment of one candidate to each object, with no Instance used twice, as the product of its constraints' scores, and orders the wanted object's candidates by their best assignment. Ties go to the earlier position in the phrase's ranking, then the lower Instance id.

The spatial part never makes a Query fail. The Query endpoint keeps its path and fields and adds four: `relations_applied` (the Relations decided the Matches), `relations_stated` (the parsed Query had a Relation), `unsupported` (the parts the Relation set cannot express, as the parser quoted them) and `parse_failed`. Unsupported parts are reported and otherwise ignored: the supported Relations still apply, and a Query with no Relation left is answered as a plain one with its original text. When no assignment is valid (a Scene with fewer Instances than objects, or objects whose only candidates are one Instance), the Query is answered as a plain one with `relations_stated` true and `relations_applied` false, which tells it apart from a Query that had no Relation. A parser reports an unusable reply by raising `QueryParseError`; the endpoint logs its reason on the Query logger and answers the plain Query with `parse_failed` true and status 200. Any other exception from a parser is a bug and fails the request. The viewer shows one line of notice whenever a part of the Query was not taken into account or the parse failed.

Each Relation is a pure function of axis-aligned boxes and centroids that returns a score in [0, 1]. Distances are gaps between boxes, not between centroids, and are measured against the Scene extent (the diagonal of the box around every Instance) through `exp(−d / (s · extent))` (`between` measures against the segment joining its two Anchors instead), so no Relation uses an absolute distance in metres. `near` is the falloff of the gap, 1 when the boxes touch or overlap. The ordering Relations (nearest to, farthest from, largest, smallest, tallest, lowest) score a candidate by its place among all the candidates of its object, by gap to the assignment's Anchor, box volume, vertical extent or the height of the box's bottom: the first distinct value scores 1, the last 0, evenly spaced, so tied candidates share a score and a tie takes one step. An Anchor that is also a candidate of the subject (two objects with one phrase) stays in that order, so standing a subject candidate in for the Anchor cannot thin out the candidates it is compared with. The other Relations follow the spec; a Relation without a scoring function fails loudly.

## Considered Options

- Geometry code written by a language model per Query (LaSP, ZSVG3D): flexible, but runs generated code, and a wrong program fails silently or not at all.
- The full QVR3D pipeline, where a vision-language model scores attributes and Relations per candidate and View: many generations per Query, and its own ablation credits most of its gain to choosing Views by Query, which is a later slice.
- Models trained on ScanNet-style data (Open3DSG, Chat-Scene, LLaVA-3D, 3D-VisTA): trained on sensor scans with fixed classes, not on Reconstructions from photos, and each adds a model to the GPU stack.
- A precomputed scene graph: fixes the Relations and their thresholds at job time, so older Scenes would need reprocessing for every change.
- A keyword test that decides whether a Query is spatial: misses paraphrases and other languages; every Query goes through the parser instead.
- Boolean Relations with distance thresholds: noisy boxes would remove the right candidate instead of lowering its score, and one threshold cannot fit a desk top and a hall.
- Relations as a third Reciprocal Rank Fusion channel: an Instance that fits the phrase well but breaks the Relation could still win.
- An absolute similarity threshold on candidates: similarities sit on different, uncalibrated scales per channel and per Scene, and a threshold could leave an object without candidates. The relative candidate margin was chosen instead.
- No margin, only the first M of the phrase ranking: the ranking is relative too, so with fewer than M fitting Instances the rest of the shortlist is filled with Instances that do not fit, and the Relations, which order the Matches, can pick one of them.

## Consequences

Matches of a spatial Query are ordered by the Relation score; the phrase ranking only picks the candidates and breaks ties, so a candidate that is not what the phrase names can win ("the largest chair" in a Scene with one chair could return a sofa). The candidate margin reduces this but does not remove it: too wide and the sofa stays, too narrow and a second real chair is dropped. The image channel is the likelier leak, because an Instance passes on either channel and image similarities sit in a narrow range. A Scene with nothing that fits a phrase still gives that object a candidate, the best of a poor shortlist, since a relative margin cannot tell that the best is poor.

The candidate margin limits which Instances may stand in for an object of a spatial Query. It is not the relevance threshold on Matches that ADR 0008 removed: it compares Instances with the best of their own shortlist, never with a fixed value, it always leaves a candidate, and it applies only to the objects of a Query that has a Relation. A Query without a Relation still returns `query_top_k` Matches with no threshold.

A Match's score for a spatial Query is its assignment score, comparable only within one Query; its similarities are those of the wanted object's phrase, and it carries the Anchors of its assignment, which the viewer marks in their own colour. M, the two candidate margins, the falloff fraction and the Relation formulas are starting guesses, not validated. Bounding boxes are axis-aligned and yaw is arbitrary, so gaps between diagonal objects are underestimated. Every Query will wait for one generation of the parser, including Queries without a Relation.
